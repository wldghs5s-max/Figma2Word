## 1. 개요 및 문제 정의

Figma2Word는 초기 보고서 및 제안서 문서(A4 세로/가로 중심)를 주 타깃으로 개발되었으나, 실무 환경에서는 1920×1080, 1920×1170 등 16:9 및 16:10 비율의 **웹 UI/대시보드 기획안 및 화면 설계서**를 DOCX로 변환해야 하는 수요가 급증하고 있다.

실제 실전 웹 프로젝트인 `펜테크 3차 디자인`을 분석한 결과, 기존 페이지 전략(`resolveScale`)의 한계로 인해 다음과 같은 심각한 규격 및 레이아웃 문제가 발생했다.

1. **20인치 초대형 페이지 생성**:
   - 1920px 너비의 웹 화면이 A4 비율 판정(`1.35 ~ 1.50`)에 걸리지 않아 기본 CSS 스케일(`0.75 pt/px`, 96 DPI → 72 pt/in)로 변환됨.
   - 결과 페이지 너비가 **1,440 pt (20인치 / 50.8 cm)** 에 달하여, Word에서 100% 배율로 볼 때 극심한 가로 스크롤을 유발하고 일반 프린터 출력이 불가능함.
2. **동일 문서 내 극단적 페이지 규격 불일치**:
   - 모달 팝업(`필터`: 504×613 px → 378×459.75 pt, 약 5.25인치)
   - 일반 화면(`Desktop - 1`: 1440×1024 px → 1080×768 pt, 약 15인치)
   - 웹 대시보드(`Desktop - 대시보드`: 1920×1170 px → 1440×877.5 pt, 약 20인치)
   - 플러그인 측정 가이드(`📏 Container`: 1920×3361 px → 1440×2520.75 pt, **35인치!**)
   - Word 사양상 최대 허용 페이지 크기(22인치 / 1,584 pt)를 초과하여 렌더링이 잘리거나 레이아웃 엔진 경고가 발생하는 문제 발생.
3. **인접 페이지 캔버스 충돌 (Multi-Page Canvas Collision)**:
   - 인접한 두 페이지의 크기가 동일할 때 섹션 브레이크(`<w:sectPr>`) 생략으로 인해 페이지가 겹쳐 렌더링되는 치명적 버그 발생 (작업 E에서 상세 분석).

## 2. 기존 페이지 스케일링 로직 (`resolveScale`) 정밀 진단

기존 `src/canvas/types.ts`의 `resolveScale()` 구현:

```typescript
export function resolveScale(
  frameWidth: number,
  frameHeight: number,
  scalePolicy?: PageScalePolicy,
  customScale?: number
): { scale: number; pageSize: { widthPt: number; heightPt: number } } {
  // 1. 커스텀 스케일 지정 시 우선 적용
  if (scalePolicy === "custom" && customScale) { ... }

  // 2. A4 자동 판별 로직
  const aspectRatio = frameWidth / frameHeight;
  const isA4Landscape = aspectRatio >= 1.35 && aspectRatio <= 1.50; // A4 비율: 1.414
  const isA4Portrait = aspectRatio >= 0.65 && aspectRatio <= 0.75;  // A4 세로 비율: 0.707

  if (isA4Landscape) {
    const scale = A4_LANDSCAPE_WIDTH_PT / frameWidth; // 841.89 / frameWidth
    return { scale, pageSize: { widthPt: 841.89, heightPt: 595.28 } };
  }
  // ...
  // 3. Fallback: 웹 UI 등 비 A4 비율
  const scale = 0.75; // 1px = 0.75pt (CSS 96dpi -> Word 72dpi)
  return { scale, pageSize: { widthPt: frameWidth * scale, heightPt: frameHeight * scale } };
}
```

### 진단 결과
- 웹 UI의 표준 해상도인 1920×1080 (비율 1.777) 및 1920×1170 (비율 1.641)은 A4 Landscape 비율 범위(`1.35 ~ 1.50`)를 크게 벗어남.
- 따라서 무조건 3단계 Fallback(`scale = 0.75`)으로 빠지게 됨.
- 이로 인해 1920px 화면은 `1920 * 0.75 = 1440 pt`의 광활한 비표준 규격으로 Word에 직렬화됨.

## 4. 전략별 실증 테스트 결과

### 4.1 전략 1 (Native Canvas: 1440×810 pt / 1440×877.5 pt)
- **장점**: 폰트 크기가 10.5pt, 12pt 등으로 Word 내에서 매우 또렷하게 보임.
- **치명적 단점**:
  1. Word 뷰어가 20인치 폭을 표시하느라 100% 뷰에서 화면의 절반만 보이고 우측이 잘림.
  2. 고객사에 전달 시 "페이지 크기가 왜 이렇게 비정상적으로 큰가?"라는 반응 유발.
  3. Word의 최대 규격 한계(22인치)에 근접하여 3361px 가이드 프레임의 경우 2520pt로 초과되어 심각한 레이아웃 파손 유발.

### 4.2 전략 2 (A4 Landscape Fit: 841.89 × 473.56 pt)
- **장점**:
  1. A4 용지 규격(841.89 × 595.28 pt) 내에 높이 여백(상하 약 60pt)을 두고 완벽하게 들어감.
  2. PDF 내보내기 시 일반 프린터에서 용지 걸림이나 잘림 없이 100% 인쇄 가능.
  3. Word 기본 창 크기에서 가로 스크롤 없이 전체 페이지가 한눈에 들어옴.
- **고려사항**:
  - 14px 폰트가 약 6.14pt로 축소되므로, Word 화면 줌 120~150% 또는 PDF 뷰어에서 확대하여 보아야 함.
  - 하지만 기하학적 종횡비(Aspect Ratio)와 요소 간 상대 좌표/여백은 100% 정확하게 보존됨.

## 5. 최적 권장 아키텍처: 프레임 인식형 적응형 전략

Figma2Word의 범용성을 위해 다음과 같은 계층적 페이지 정책 설계를 확립한다.

### 5.1 `PageScalePolicy` 옵션 확장

```typescript
export type PageScalePolicy =
  | "fit-a4"          // 기본값: 문서 의도에 맞춰 A4에 최적 맞춤 (웹 UI는 A4 가로 맞춤)
  | "native-canvas"   // 원본 1:1 CSS 스케일 (0.75 pt/px)
  | "presentation"    // 16:9 슬라이드 프레젠테이션 규격 (960x540pt 또는 841.89x473.56pt)
  | "custom";         // 사용자 명시 스케일 배율
```

### 5.2 웹 UI 프레임 판별 및 통합 배율 산출 알고리즘
- 문서 내 탑레벨 프레임들의 너비 분포를 분석하여 **주 화면 해상도(Primary Screen Width)**를 결정함 (예: 1920px).
- `scale = 841.89 / primaryScreenWidth` (1920px 기준 `scale = 0.43848`).
- **일관성 보장 원칙**:
  - 동일한 웹 UI 플로우 내의 서브 화면(예: 1920×1170 화면과 1920×1080 화면)은 동일한 스케일(`0.43848`)을 적용하여, 페이지를 넘길 때 폰트 크기나 버튼 크기가 갑자기 커지거나 작아지는 지터(Jitter)를 완전히 방지함.
  - 팝업/모달(504px 등)은 화면 내 상대 크기를 보존하거나 독립 페이지일 경우 중앙 정렬 배치.

### 5.3 비화면 아티팩트/플러그인 오버레이 사전 필터링
- `📏 Container`와 같은 Redline/Measure 플러그인 그룹은 페이지 후보에서 자동 제외하여, 35인치 거대 페이지가 생성되는 근본 원인을 사전 차단함.

## 6. 결론

1. 무조건적인 전역 폰트 축소나 임의 좌표 이동을 금지하되, **A4 Landscape 기준의 엄밀한 기하학적 비례 스케일링**을 웹 UI 문서의 기본 전략으로 채택한다.
2. 사용자가 원본 크기를 선호할 경우를 대비하여 `PageScalePolicy`를 설정 가능하도록 개방한다.
3. 가장 중요한 것은 **각 페이지별 독립 섹션 브레이크(`<w:sectPr>`)를 반드시 방출**하여, 어떤 페이지 전략을 취하더라도 다중 페이지 캔버스 겹침 현상이 발생하지 않도록 렌더러를 정상화하는 것이다.
