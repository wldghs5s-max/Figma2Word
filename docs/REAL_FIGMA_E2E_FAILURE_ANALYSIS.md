(REAL_FIGMA_E2E_FAILURE_ANALYSIS)

- **분석 일시**: 2026-10-07
- **분석 대상 실제 DOCX 파일**:
  1. `debug/real-figma-whole.docx` (전체 Figma 프로젝트 URL 변환 결과, 185 KB)
  2. `debug/real-figma-frame.docx` (특정 단일 Frame URL 변환 결과, 13.6 KB)

## 1. 개요 및 핵심 진단 요약

Phase 4.1 완료 후 실제 복합 비즈니스 디자인(보험 보장분석 요약 대시보드)을 입력으로 한 E2E 실사용 검증에서 두 가지 극단적인 현상이 보고되었습니다:

1. **Test A (전체 Figma 프로젝트 변환)**:
   - DOCX 크기 약 185KB.
   - Word에서 열면 첫 페이지만 일부 보이고, **이후 스크롤이 불가능하며 Word 프로세스가 심각하게 동결(Freeze/Hang) 또는 극심한 렉 발생**.
2. **Test B (특정 단일 Frame 변환)**:
   - DOCX 크기 약 13.6KB.
   - Word가 정상적으로 열리고 스크롤도 원활함.
   - 그러나 **레이아웃이 총체적으로 붕괴되어 개별 요소들이 무작위 파편처럼 분리·적층됨**.

두 DOCX 파일의 내부 OpenXML(`word/document.xml`)을 압축 해제하여 태그 수준에서 역공학 분석한 결과, **두 현상의 명확한 구조적 원인과 메커니즘이 완전히 규명되었습니다.**

## 3. Test A: 전체 파일에서 Word가 멈추는 결정적 원인 (Q1 분석)

### 3.1 7.11 MB OpenXML과 4,817개 Table의 연쇄 충돌
- `real-figma-whole.docx`는 ZIP 압축으로 인해 파일 크기가 185KB로 작아 보이지만, **압축을 풀면 `document.xml` 단일 파일 크기만 7.11 MB에 달합니다.**
- 핵심은 XML 크기 자체가 아니라, **그 7.11 MB 안에 들어 있는 4,817개의 Table과 11단계에 달하는 중첩 깊이(Nested Table Depth 11)**입니다.

### 3.2 테이블 중첩 깊이별 분포 (`Table Depth Histogram`)
```text
Depth 1:   11개 (캔버스 최상위 11개 화면 Frame)
Depth 2:   44개
Depth 3:   88개
Depth 4:  274개
Depth 5:  932개  <-- 본격적인 폭발 구간
Depth 6:  910개
Depth 7:  992개
Depth 8:  928개
Depth 9:  425개
Depth 10: 185개
Depth 11:  28개
```

### 3.3 Microsoft Word 레이아웃 엔진의 렌더링 한계 초과
1. **중첩 테이블의 지수적 레이아웃 계산 복잡도**:
   - WordprocessingML 렌더러는 테이블 안의 테이블(Nested Table)을 렌더링할 때, 바깥 셀의 폭과 안쪽 셀의 폭, 텍스트 줄바꿈, 테두리 결합을 상호 참조하며 재귀적으로 너비를 계산합니다.
   - 깊이 5~8단계 구간에만 각각 900개 이상의 테이블이 집중되어 있으며, 모든 테이블이 `w:type="pct" w:w="5000"` (부모 대비 100% 너비)로 정의되어 있습니다.
   - Word가 하나의 셀 너비를 결정하기 위해 하위 10단계 자식 테이블들을 수만 번 재귀 순회(Reflow)해야 합니다.
2. **단일 섹션(Single Section)과 페이지 분할(Pagination) 동결**:
   - 11개의 서로 다른 모바일/웹 전체 화면(수천 개의 UI 요소)이 섹션 분할(`w:sectPr`)이나 페이지 브레이크(`w:br type="page"`) 없이 **단 하나의 연속된 Body Flow**로 묶여 있습니다.
   - Word는 4,817개의 중첩 테이블을 수백~수천 페이지의 종이로 자르고 나누는 페이지 분할 알고리즘을 실행하다가 **렌더링 UI 스레드가 100% CPU 동결 상태**에 빠지게 됩니다. 이것이 첫 페이지만 간신히 뜨고 이후 스크롤이 불가능해지는 직접적인 물리적 원인입니다.

## 4. Test B: 특정 Frame에서 레이아웃이 총체적으로 깨지는 원인 (Q2 분석)

Frame 변환 결과(`real-figma-frame.docx`)는 텍스트 노드가 단 62개에 불과한 작은 단일 화면입니다. 따라서 Word 자체는 멈추지 않고 열립니다. 그러나 왜 레이아웃이 "고기 파편"처럼 깨지는가?

### 4.1 원인 1: 텍스트 62개 대비 테이블 88개 — 모든 시각 요소의 100% 폭 테이블화
- `docxRenderer.ts`의 구현을 보면:
  - `renderShape`: 사각형(Rectangle) 노드에 fill/stroke가 있으면 **무조건 폭 100%의 1x1 Word Table**로 변환합니다.
  - `renderContainer`: 컨테이너(Frame, Group)에 배경색이나 테두리가 있으면 **무조건 폭 100%의 1x1 Word Table**로 감쌉니다.
- 실제 피그마 디자인 분석:
  - 피그마에는 화면 배경, 섹션 카드뿐만 아니라 **"작은 뱃지(2건, 7건)", "태그 배경", "아이콘 배경 사각형", "작은 컬러 도트/칩"** 등 수많은 작은 사각형들이 존재합니다.
  - 이 20px~30px 크기의 작은 장식 도형들이 **전부 가로 100%짜리 거대한 Word Table 블록으로 변환**되었습니다.
  - Word에서 Table은 단락과 마찬가지로 줄바꿈을 강제하는 Block 요소입니다. 따라서 나란히 있어야 할 라벨, 뱃지, 숫자가 전부 세로로 한 줄씩 분리되어 위아래로 길게 적층됩니다.

### 4.2 원인 2: 테이블 중첩 7단계로 인한 셀 가용 너비 소멸
- 실제 Frame DOCX의 최상위부터 최하위까지의 OpenXML 태그 추적:
  ```text
  <w:body>
    <w:tbl> <!-- 최상위 화면 Frame (배경 #EDF9FC) -->
      <w:tc>
        <w:tbl> <!-- 메인 카드 그룹 -->
          <w:tc>
            <w:tbl> <!-- 요약 카드 -->
              <w:tc>
                <w:tbl> <!-- 내부 헤더 -->
                  <w:tc>
                    <w:tbl> <!-- 뱃지 래퍼 -->
                      <w:tc>
                        <w:tbl> <!-- 뱃지 사각형 (배경 #3887F5) -->
                          <w:tc>
                            <w:p><w:r><w:t>"7건"</w:t></w:r></w:p>
  ```
- 7단계를 파고들면서 각 테이블의 여백(Margin), 패딩(Padding), 테두리가 누적되어, 가장 안쪽 셀의 실제 가용 폭은 몇 밀리미터 단위로 축소됩니다.
- 그 결과 텍스트가 가로로 온전히 흐르지 못하고 한 글자씩 쪼개지거나 레이아웃 밖으로 튀어나갑니다.

### 4.3 원인 3: UI 계층 트리(Figma Nested Frames) vs 문서 계층 모델(Word Flow)의 불일치
- 피그마 디자이너는 오토레이아웃과 컴포넌트를 만들 때 수많은 Frame 안에 Frame, 그 안에 Frame을 감싸서 레이아웃 구조를 잡습니다.
- 현재 엔진은 이를 Word의 시각적 박스(Table with Shading)로 1:1 매핑하고 있으므로, 피그마의 레이아웃 그룹핑 계층이 Word에서는 **"테이블 안에 갇힌 테이블의 연속"**이 되어 버립니다.

## 5. 전체 파일과 단일 Frame의 파이프라인 비교 (Q2 추적)

```text
[전체 파일 URL (?node-id=0-1 또는 node-id 생략)]
  DOCUMENT
    └─ CANVAS (0-1)
        ├─ Screen 1 (Frame: 보장분석 요약, x=0, y=0)
        ├─ Screen 2 (Frame: 보장 상세분석, x=450, y=0)
        ├─ Screen 3 (Frame: 부족보장 리모델링, x=900, y=0)
        └─ ... (총 11개 스크린 프레임)

[단일 Frame URL (?node-id=123-456)]
  FRAME (Screen 1: 보장분석 요약)
    ├─ Background Rectangle
    ├─ Header Area
    └─ Content Cards
```

### 5.1 전체 파일에서 발생하는 치명적 현상 4가지
1. **Canvas Flattening 버그**:
   - `figmaParser.ts`의 `case "CANVAS"`는 `return this.parseChildren(node.children)`으로 하위 모든 스크린을 단일 평면 리스트로 합칩니다.
   - 11개의 완전히 독립된 화면들이 페이지 구분 없이 단일 본문 흐름에 한꺼번에 쏟아집니다.
2. **Cross-Frame LayoutEngine 간섭**:
   - `clusterHorizontalRows()`와 `foldContainedOverlays()`가 캔버스 전체 노드를 대상으로 실행됩니다.
   - Screen 1(x=0, y=0)과 Screen 2(x=450, y=0)는 Y좌표가 0으로 동일하므로, LayoutEngine이 **서로 다른 스크린들을 같은 행(Row)으로 묶으려고 시도**하거나 상호 간섭이 발생합니다.
3. **거대 캔버스 전역 좌표와 프레임 상대 좌표의 혼선**:
   - Figma Canvas 상에서 프레임들은 (0, 0), (1200, 0) 등에 배치되는데, Word는 전역 좌표 캔버스가 없으므로 이 거대한 수평 배치가 수직으로 무작위 적층됩니다.
4. **계산 복잡도 폭발**:
   - 수천 개 노드에 대해 $O(N^2)$의 Bounding Box Containment 검사와 Row Clustering이 반복 수행됩니다.

## 7. 근본 원인에 대한 해법 판단 (Option 선택 및 근거)

### [후보 Option 검토]
- **Option A (현재 구조 유지 + 최소 수정)**:
  - 불가능. 현재 렌더러가 컨테이너/도형마다 무조건 Table을 생성하는 구조를 그대로 두면 중첩 테이블 7~11단계 문제를 피할 수 없음.
- **Option B (LayoutEngine 특정 단계 재설계)**:
  - 부분적 필요. Canvas 직하위의 메인 Frame들을 개별 Page/Section으로 격리하는 전략이 필수적임.
- **Option C (IR 및 렌더링 전략 고도화 — 권장 및 핵심)**:
  - **선택: Option B + Option C의 구조적 결합**
  - 근거:
    1. **Canvas 처리 분리 (Option B)**: Canvas 직하위의 최상위 Frame들은 단일 flow로 flatten하지 않고, 각각을 독립된 Word 페이지(`Page Break` 또는 `Section`)로 명확히 분리하여 Cross-Frame 간섭을 원천 차단해야 합니다.
    2. **Table 래핑 기준의 엄격화 (Option C)**:
       - 모든 Rectangle이나 작은 Container를 Table로 감싸지 말아야 합니다.
       - 내용물이 없는 단순 도형이나 작은 뱃지/아이콘은 Table이 아닌 인라인 도형/텍스트 또는 그룹 내부 요소로 처리해야 합니다.
       - Table Nesting 허용 깊이를 제한하거나(예: 최대 2~3단계), 순수 레이아웃용 투명 Frame은 Table 없이 단락/흐름으로 평탄화(Flatten)해야 합니다.
- **Option D (DOCX 변환 전략 자체 포기)**:
  - 부적합. Word 문서 변환이라는 프로젝트 헌장의 본질을 유지하면서, 위 Option B+C의 정돈된 아키텍처 규칙을 도입하면 완벽히 해결 가능함.

## 8. 결론 및 향후 진행 권고

1. **현재 상태 진단 요약**:
   - Phase 4.1-A에서 구현한 `CANVAS` 처리로 인해 데이터 추출 자체는 성공했으나, **Canvas 상의 다중 화면을 하나의 단일 플로우로 합친 점**과 **렌더러의 무제한 중첩 Table 생성**이 결합되어 7.1MB/4,817개 테이블이라는 재앙적 OpenXML을 발생시켰습니다.
   - 단일 Frame에서도 동일하게 1x1 Table 남발로 인해 레이아웃이 찢어지는 현상이 관찰되었습니다.
2. **코드 수정 전 분석 완료 확인**:
